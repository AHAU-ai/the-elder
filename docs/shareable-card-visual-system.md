# Shareable Card — Visual System

Status: implemented.
Decided: 2026-08-15 (AI-art question first raised in an earlier session;
settled here). Last updated: 2026-08-21 (AI-generated floral frame
garlands added, additive to the hand-drawn Flower component — see
"Floral frame garlands, additive" below).

Prior update: 2026-08-18 (marker landscapes added — see "AI-generated
imagery, revisited" below; this reverses the original "never" and the
reasoning for the reversal is recorded here as deliberately as the
original prohibition was).

This is a decision record. It documents what was chosen and why, so the
reasoning survives outside a chat thread. It is not a spec — where this
document and the code disagree, the code is what ships, and this file
should be corrected.

## Original decision: no AI-generated imagery, ever (2026-08-15)

The card (`app/components/ShareableCard.tsx`) needed a visual field beyond
plain text. A diffusion model was considered and rejected: asked for
K'iche'/Ifá/Theravada-adjacent visuals, it produces ceremonial-looking
fabrication trained on scraped, unauthorized source imagery — the same
integrity violation Lineage Integrity of Voice exists to prevent, just in
a picture instead of a sentence. A fabricated image is indistinguishable
to the seeker from an authentic one, which makes it worse than a
fabricated sentence, not better.

The fix that fit at the time: a **templated visual system**, not a
generated one. Every marker (wound / threshold / pattern / exile / figure)
has a fixed glyph, and every authorized voice has a fixed accent color
(`lib/mythopoetics/cardConfig.ts`, `MARKER_GLYPHS` / `accentForVoice`).
The glyph *is* the card's art. This is the same authorization-artifact
logic as the rest of the card: nothing appears that wasn't deliberately
placed there by someone accountable for it.

Per-voice accent overrides are gated by `AUTHORIZED_ACCENTS` — a voice
only gets its own color once its tradition-bearer has reviewed it,
independent of whether the voice itself is authorized to speak. Everything
unreviewed renders with the shared default gold.

## AI-generated imagery, revisited (2026-08-18)

The card gained a landscape background per marker archetype (five images,
`public/card-landscapes/`, generated by
`scripts/generate-marker-landscapes.mjs` via Gemini image generation).
This is AI-generated imagery on the card — the thing the original decision
said "not an invitation to revisit."  It was revisited anyway, at the
project owner's explicit direction, on the following narrower basis that
the original prohibition's actual harm analysis still supports:

The harm identified above was never "AI imagery" as such — it was
**fabricated ceremonial/cultural representation of a specific tradition,
shown as if authentic, without that tradition's consent.** The five
landscape images do not do that: the generation prompts (see the script)
explicitly exclude people, ritual objects, and any culturally- or
religiously-specific iconography, and are scoped to *marker archetype
only* — never to voice or tradition. A "threshold" landscape is a stone
archway and light; it is not Delphi, not a K'iche' doorway rite, not
anything claiming to belong to a named culture. No tradition-bearer
consent question applies because no tradition is depicted, authorized or
not.

This scoping is load-bearing, not decorative:
- **Marker-only, never voice-tied.** Tying imagery to `voiceKey` was
  explicitly considered and rejected — several voices
  (`babalawo`, `mekubal`, `chukchi_shaman`; see `src/resilience/flags.ts`)
  are documented as lacking tradition-bearer/cultural-authority consent
  even to have their corpus content live, let alone generated imagery
  depicting them. Marker-only sidesteps that entirely rather than
  threading a narrower consent needle.
- **Cached, not dynamic.** Generated once per marker and committed to
  `public/`, not called at share/request time — bounded, auditable output
  (five known images, reviewable by anyone) rather than an open-ended
  generator that could drift into depicting something unintended on a
  future prompt tweak.
- **A person looked at all five outputs before they shipped**, same
  authorization-artifact principle as the glyph/accent system: nothing on
  the card exists because a model produced it unsupervised.

**If a future pass wants more images (more markers, per-line variation,
etc.):** the same three constraints apply — no tradition/culture-specific
content, no per-voice tying without an actual consent process, and no
live/dynamic generation. Loosening any of those three is the part that
would need to come back to this document, not the general "is AI imagery
allowed at all" question, which this section already settled.

## Floral frame garlands, additive (2026-08-21)

A second AI-generated layer was added to the card: one floral garland
image per marker archetype (`public/card-flowers/`, generated by
`scripts/generate-marker-frame-flowers.mjs`), composited into
`ShareableCard.tsx` behind the existing hand-authored `Flower` SVG
component — additive, not a replacement. The hand-drawn blooms stay the
foreground focal points (parallax-driven, accent-colored to match the
reading's own voice); the AI garland reads as an atmospheric enrichment
layer behind them, screen-blended along the top edge.

This is governed by the same three constraints as the landscapes above,
applied identically, not loosened:

- **Marker-only, never voice-tied.** Same five archetypes, same reasoning
  (`babalawo`/`mekubal`/`chukchi_shaman` still lack the consent this would
  require if tied to voice or tradition).
- **Cached, not dynamic.** Generated once, committed to
  `public/card-flowers/`, never called at request/share time.
- **A person looked at all five outputs before they shipped.** Reviewed
  twice: once by the implementing session for obvious defects (text/
  watermarks, accidental culturally-specific flower forms — the `figure`
  variant's rounded petal layering was flagged as lotus-adjacent and
  raised explicitly), then by the project owner, who approved all five as
  generated.

One additional constraint specific to this layer, not present for the
landscapes: **no flower with a strong named-culture or named-religion
association.** The generation prompt (see the script) explicitly excludes
lotus, marigold, chrysanthemum, hibiscus, cherry blossom, and jasmine by
name — generic wildflowers, thorned vines, and small elemental blooms
only. This exists because unlike bare landscape elements (rock, light,
water), specific flowers carry real, recognizable cultural and religious
meaning in a way "a stone archway" does not — the same harm the original
2026-08-15 prohibition was written to prevent, narrowly reintroduced here
under the same scoping logic as the 2026-08-18 landscape reversal.

**Compositing note, not a governance point but worth recording:** the
generator renders on pure black (`#000000`) rather than a transparent
background, because diffusion image models don't reliably respect alpha
channels. `ShareableCard.tsx` composites with `mix-blend-mode: screen`
instead — the same technique this file already used for its grain-texture
layer. Verified in isolation (a minimal static-HTML harness, screenshotted
via headless Chromium) that the black background is fully invisible
against the card's obsidian field before wiring it into the live
component.

## Layout: content-sized, not fixed-aspect

The card was originally `aspectRatio: '4 / 5'` with `overflow: hidden`. That
produced two visible bugs:

- Short quoted lines left a large dead margin (empty space).
- Long quoted lines pushed the dedication line and footer past the fixed
  height, and `overflow: hidden` clipped them silently (disappearing text).

Fixed by dropping the fixed aspect ratio for a `minHeight` floor — the card
now sizes to its actual content. This only works if content has a real
ceiling, so a length cap was added on the display side
(`MAX_LINE_CHARS = 170` in `ShareableCard.tsx`).

## Line selection: last-sentence pull, only past the cap

`line` reaches `ShareableCard.tsx` two ways, from two call sites:
`CouncilTabs.tsx`'s "Keep This Gift" → `onKeepAsCard` passes
`content.returnGift` from `lib/psychopompLayer.ts` unedited — a full
paragraph (~250-315 characters), not a short line; `Threshold.tsx`'s
"Make this your card" (a text-selection popover over the reading) passes
whatever the seeker deliberately highlighted, usually already short but
not guaranteed to be.

If the text already fits under the cap, it's shown exactly as given —
untouched. That matters even for the auto-populated case: some
`returnGift` paragraphs are themselves short and multi-sentence (*"What is
in your prohairesis... And the duty you now return to, undistorted."*,
142 chars), and always extracting "the last sentence" would silently drop
the first sentence even though nothing needed cutting.

Only past the cap does extraction kick in, and it takes the *last*
sentence rather than truncating from the front. That prose is
consistently written to close on a short, aphoristic final sentence —
*"Delphi gives the question, not the answer."*, *"The return gift must be
given, not kept."* — so the last sentence beats keeping the setup and
cutting the payoff.

If `returnGift` copy is ever rewritten, keep ending each one on a short,
self-contained closing clause — the over-cap path depends on that
convention, not just on length.

## Share-link content mismatch (fixed)

`createShareLink()` used to POST the raw `line` prop to `/api/share`,
not `displayLine` (the `pullQuote()` output actually rasterized into the
PNG via `html-to-image`). `shareLedger.ts` stores up to 500 characters
and `SharedCardView.tsx` (the public `/share/[id]` page) renders whatever
was stored — so a signed-in seeker's downloaded/shared image could show
the short pulled quote while the public link and Journal entry
(`MythicJournal.tsx`) showed the full uncut paragraph. Fixed by sending
`displayLine` instead: what's rasterized is now what's persisted and
what's public.

## CardQuote: making the mismatch impossible to reintroduce, not just fixed

The bug above was found by manually tracing every consumer of `line` —
that guarantee decays the moment a new consumer is added and nobody
re-traces. `CardQuote` (`lib/mythopoetics/cardConfig.ts`) turns it into a
type: `type CardQuote = string & { readonly __brand: 'CardQuote' }`,
producible only by `pullQuote()`.

`ShareableCard`'s `line` prop, `shareLedger.createShareCard`'s `line`
param, and `ShareCardEntry.line` all require `CardQuote`, not `string`.
`ShareableCard.tsx` no longer calls `pullQuote()` internally — callers
(`CouncilTabs.tsx`, `Threshold.tsx`) call it before setting `cardLine`
state, so the exact same value is what's rasterized into the PNG and
what's sent to `/api/share`; there is no second "raw line" anywhere in
the render path for a future edit to send to only one of them.

Two sanctioned casts re-establish the brand where compile-time checking
can't reach:

- `app/api/share/route.ts` — the request body arrives over the wire as an
  unchecked string, so the brand can't be trusted by construction here.
  The route now validates against the real ceiling (`MAX_LINE_CHARS`,
  exported from `cardConfig.ts` — previously a looser, separate `500`)
  before casting, so a modified or hostile client can't bypass the
  branding client-side and post a full paragraph anyway.
- `shareLedger.ts`'s `rowToEntry` — casts `row.line` back to `CardQuote`
  on the strength of `createShareCard` being the only writer.

What this doesn't cover: any future code that reads `share_card.line`
outside this type graph (a raw SQL query in a new script, a hand-rolled
admin view) bypasses the brand entirely — it's a compile-time guarantee
for TypeScript callers, not a database-level constraint.
